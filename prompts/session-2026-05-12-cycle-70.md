## What surprised the implementation

### 1. Token rotation mid-session
The first SUPABASE_ACCESS_TOKEN worked for initial schema reads, then started returning 401 a few minutes later. Had to ask for a fresh token before running migrations. Pattern to watch: assume Supabase Management API tokens are short-lived enough that they may rotate within a single cycle's work. Don't structure tasks around assuming the token will last.

### 2. Pre-existing RLS infinite-recursion in `company_memberships`
The `company_memberships_read_by_company_member` policy does:
```sql
USING (
  EXISTS (
    SELECT 1 FROM company_memberships cm
    WHERE cm.company_id = company_memberships.company_id
      AND cm.user_id = auth.uid()
      ...
  )
)
```
The recursive SELECT triggers Postgres error 42P17 ("infinite recursion detected in policy") when an anon-role PostgREST query traverses it. My first cut of `seller_services_select_owner` used the same EXISTS pattern, which transitively poisoned anon-role reads on `seller_services` (anon doing `/rest/v1/seller_services` got the same recursion error). Mitigation in this cycle: re-scope all owner-side policies on `seller_services` to `TO authenticated`, so anon-only ever evaluates the `select_active_public` policy. The underlying bug in `company_memberships` remains — flagged for Cycle 71+. Doesn't affect Cycle 70's surfaces because all reads go through `createAdminClient()` (bypasses RLS).

### 3. Schema drift vs. prompt assumptions
The prompt's RLS policies used `company_memberships.profile_id`, but the actual column is `user_id` (pre-existing schema decision). Also, the prompt assumed `company_memberships.title` existed for custom role labels — it doesn't, only the `role` enum (`owner`/`admin`/`member`). Adapted: `TeamMemberData.role` maps the enum directly (`Owner`/`Admin`/`Member`); when a `title` column eventually lands, it can drop in as a precedence layer in `getPublicTeamForCompany`.

### 4. `moddatetime` extension not installed
The prompt's migration script used `moddatetime` for the `updated_at` trigger. That extension isn't installed in this project. Swapped to `public.handle_updated_at()` which is already defined and used by `profiles`, `listings`, `subscriptions`, etc.

### 5. `import 'server-only'` blocks vitest
Putting the pricing/SLA formatting helpers inside `services.ts` (which has `import 'server-only'`) caused vitest to refuse to transform the test file (`server-only` throws when imported in jsdom). Split the pure helpers into `src/lib/profile/services-format.ts` (no `server-only`) and re-export them through `services.ts`. The `ServiceCard` component and the test file both import from `services-format.ts` directly.

### 6. Zod 4 stricter UUID validation
Zod 4 (`^4.3.6`) rejects all-1s UUIDs like `11111111-1111-1111-1111-111111111111` because the version nibble is 1, not 4-8 per RFC 4122. Tests failed silently until I switched to canonical v4 UUIDs generated by `crypto.randomUUID()`.

### 7. PostgREST `profiles` join ambiguity
`company_memberships` has two FKs to `profiles`: `user_id` and `invited_by`. PostgREST refused the embed without a column hint. Fix: `profiles:profiles!user_id ( id, display_name, full_name, avatar_url )`. Cycle 69's existing queries got away without the hint because they only joined `profiles` via `user_id` and the syntax was implicitly resolvable. Adding the explicit hint future-proofs the query.
