## Cycle 54 — Auth: Single Sign-In Method & Password Reset Fix (v4.25.0)

### Outcome
- Users who register with Google/Apple can no longer accidentally sign in with email+password (and vice versa). Both layers of defense in place: a dashboard recommendation to disable Supabase auto-linking plus a code-level guard in the OAuth callback.
- Password reset no longer silently logs users in. Post-update they're explicitly signed out and sent to `/login?reset=success` with a green confirmation banner.
- All auth error copy is now specific and actionable via `friendlyAuthError()`.

### Critical research findings (pre-implementation)
The codebase had **zero** identity-provider detection before this cycle. `src/app/(auth)/callback/route.ts` never read `data.user.identities`. Login/forgot-password/reset-password were all thin wrappers over `supabase.auth.*` with no custom logic. This meant:
1. A user who signed up with Google could request a password reset and Supabase would silently drop them into the app (no password existed to reset; Supabase treats the reset link as a magic login).
2. Email users who clicked "Continue with Google" could have their identities auto-linked by Supabase, creating conflicting sessions.
3. Failed password logins showed raw Supabase error messages with no "try Google instead" hint.

### DB changes
- Created `public.get_auth_providers_for_email(p_email text) RETURNS text[]` — SECURITY DEFINER, granted to `service_role` only, REVOKEd from `anon`/`authenticated`. Returns distinct `auth.identities.provider` values for a given email, or an empty array. Applied via Supabase Management API. Smoke-tested against `mark@p5400.com` → returned `['google']` correctly.

### New files
- **`src/app/actions/auth.ts`** — `getProvidersForEmail(email)` server action wrapping the RPC. Returns `{ providers, hasPassword, primary, exists }` with a smart `primary` heuristic (single provider → that one; multi + email → email; multi no-email → first OAuth).
- **`src/lib/auth/errors.ts`** — `friendlyAuthError(rawMessage)` + `providerLabel(p)` client utilities. Maps Supabase raw errors to actionable copy; no network.

### Modified files
- **`src/app/(auth)/login/page.tsx`** — banners for `?reset=success` (green) and `?error=wrong_method&provider=<p>` (destructive); on failed password login, probes `getProvidersForEmail(email)` and shows a specific provider hint if the account is OAuth-only; visually highlights the OAuth button row with `ring-2 ring-primary` when a hint is active; wraps all Supabase errors in `friendlyAuthError()`.
- **`src/app/(auth)/forgot-password/page.tsx`** — pre-checks the provider before calling `resetPasswordForEmail()`; OAuth-only accounts get a message and no email is sent; now reads `?error=…` query param (wrapped in `<Suspense>` for `useSearchParams()` compliance).
- **`src/app/(auth)/reset-password/page.tsx`** — `useEffect` on mount calls `supabase.auth.getUser()` and redirects to `/forgot-password?error=…` if no session; after successful `updateUser({ password })`, explicitly `signOut()`s and `window.location.assign('/login?reset=success')` so middleware re-runs against the cleared cookie. Description copy clarified: "You'll log in again with it."
- **`src/app/(auth)/callback/route.ts`** — after `exchangeCodeForSession()`, inspects `data.user.identities` for both `email` AND (`google` OR `apple`). If both present, signs out and redirects to `/login?error=wrong_method&provider=email`. Guard skipped when `next=/reset-password` so password recovery isn't blocked. Welcome-email and referral tracking logic unchanged.

### Files NOT touched (deliberately)
- `src/lib/supabase/middleware.ts` — `/reset-password` is already neither a protected prefix nor an auth route, so the middleware lets recovery sessions through. No changes needed.
- `src/components/auth/oauth-buttons.tsx` — still calls `signInWithOAuth()` directly; cross-method blocking is enforced in the callback after exchange, not at click time.
- `supabase/migrations/` — no migration file written. The RPC was applied via Management API; migration squashing can pick it up later if needed.

### Verification
- `npx tsc --noEmit` → clean
- `npm run lint` → 0 errors (62 pre-existing warnings)
- `npm run build` → success
- `npm test` → 89/89 pass
- RPC smoke test: `SELECT public.get_auth_providers_for_email('mark@p5400.com')` → `['google']`

### Follow-up reminder for operator
**Disable "Enable automatic identity linking" in the Supabase dashboard** (Auth → Settings). The code-level callback guard catches linked accounts, but disabling auto-linking at the source is the primary defense and avoids the round-trip.

## Cycle 53 — SOS Response Notifications: Badge, Toast, Sound (v4.24.0)

### Outcome
SOS requesters now get an unmissable alert when a vendor responds: distinct SOS-specific tone, Sonner toast with direct "View Response" action, orange-accented dropdown entry, and a deep link that scrolls straight to the Responses section.

### Critical decision: keep `sos_response_received`, don't introduce `sos_response`
The cycle brief proposed a new `sos_response` type, but the codebase already has `sos_response_received`:
- In the `NotificationType` union (`src/app/actions/notifications.ts`)
- In the `notifications_type_check` CHECK constraint (already migrated in cycle 50.1)
- Already fired by `respondToSos()` in `src/app/actions/sos.ts`
- Already mapped in `NOTIFICATION_ICONS` / `NOTIFICATION_COLORS` in the dropdown

Renaming would break historical notifications, push-notification tag dedup (tag = type), and every rendering path. Safer to upgrade the UX around the existing canonical type. No DB migration required.

### Code changes
- **`scripts/generate-sounds.mjs`** — added `sosResponseTone()` generator and write of `public/sounds/sos-response.wav` (880→1200 Hz two-pulse, ~600 ms). Ran the script and committed the WAV.
- **`src/hooks/use-notification-sound.ts`** — added `sosResponseRef` audio element (volume 0.65), added `playSosResponse(id?)` method, added `sound: 'alert' | 'sos-response'` to `AlertTracker` interface, updated the repeat-cadence interval to dispatch to the correct audio element per tracker. Both alert types share the `highPrioritySoundEnabled` preference gate and the same acknowledge semantics.
- **`src/hooks/use-notifications.ts`** — destructured `playSosResponse` from the sound hook, added a short-circuit for `sos_response_received` that plays the SOS tone and fires a Sonner toast with 8 s duration, SOS-orange left border, and a "View Response" action button. Dependency array updated.
- **`src/components/layout/notification-dropdown.tsx`** — `sos_response_received` color → `text-[#FF6B2B]`, unread border/bg → SOS orange, `getNotificationHref()` returns `/sos/{sos_id}?tab=responses` for this type only (other SOS types unchanged).
- **`src/app/(main)/sos/[id]/page.tsx`** — added `useSearchParams` import, `useRef` for the responses section, and a post-load `useEffect` that smooth-scrolls to the responses ref when `?tab=responses` is present. Added `scroll-mt-16` to the responses container so the header doesn't overlap.

### Files NOT touched (deliberately)
- `src/app/actions/sos.ts` — `respondToSos()` already calls `createNotification('sos_response_received', ...)` with `{ sos_id, response_id }` payload; no changes needed.
- `src/app/actions/notifications.ts` — `NotificationType` union already includes `sos_response_received`; no changes needed.
- `supabase/migrations/` — the CHECK constraint already includes `sos_response_received`; no new migration.

- `npm run lint` → 0 errors (62 pre-existing warnings unrelated)

# Session 2026-04-14 — Cycle 51: Feed Comment Replies & Owner Delete (v4.22.0)

## Outcome
Shipped Facebook-style 1-level-deep threaded replies on feed comments plus hard-delete permissions for post owners and admins.

## DB changes
- `ALTER TABLE feed_post_comments ADD COLUMN parent_comment_id uuid REFERENCES feed_post_comments(id) ON DELETE CASCADE`
- `CREATE INDEX idx_feed_post_comments_parent ON feed_post_comments(parent_comment_id) WHERE parent_comment_id IS NOT NULL`
- Applied via Supabase Management API.

## Code changes
- **New:** `src/app/actions/feed-comments.ts` — dedicated server actions file containing `FeedComment` / `CommentWithReplyCount` types and `getPostComments`, `getReplies`, `addComment`, `addReply`, `deleteComment`. Helper `hydrateComments()` resolves author/company rows.
- **Refactored:** `src/app/actions/feed-posts.ts` — removed the in-file `FeedComment` interface and all comment functions; added `export type { FeedComment } from '@/app/actions/feed-comments'` for back-compat. Removed unused `safeErrorMessage` import.
- **New:** `src/app/(main)/feed/components/CommentItem.tsx` — recursive `'use client'` component. Top-level comments render Reply button, View/Hide replies toggle, and the overflow menu. Replies (isReply=true) indent `pl-8`, hide Reply button, hide reply list.
- **New:** `src/app/(main)/feed/components/ReplyInput.tsx` — pre-fills `@ParentAuthor `, auto-focuses with caret at end, Escape cancels.
- **Rewritten:** `src/app/(main)/feed/components/CommentSection.tsx` — now requires `postAuthorId` prop, uses `CommentWithReplyCount[]` state, delegates row rendering to `CommentItem`, handles deletion callbacks for both top-level and reply deletes.
- **Edit:** `src/app/(main)/feed/components/CommentInput.tsx` — import path `@/app/actions/feed-comments`.
- **Edit:** `src/app/(main)/feed/components/FeedPost.tsx` — passes `postAuthorId={post.author.id}` to CommentSection.

## Permission model (hard delete)
`deleteComment()` allows if: comment author OR post owner OR `profiles.admin_role IN ('superadmin','moderator')`. Top-level deletes count replies first, hard-delete the row (cascade removes replies), then decrement `feed_posts.comments_count` by `1 + reply_count` (clamped at 0). Reply deletes decrement by 1.

## Depth enforcement
- UI: no Reply button renders on comments where `isReply=true`.
- Server: `addReply()` fetches the parent row and throws `'Replies to replies are not allowed'` if `parent.parent_comment_id !== null`.
